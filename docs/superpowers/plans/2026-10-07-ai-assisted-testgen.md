# AI 輔助測資提案 — 實驗計畫

> 設計依據：[`specs/2026-10-02-ai-assisted-testgen-design.md`](../specs/2026-10-02-ai-assisted-testgen-design.md)（機制、文獻、四項規則、實驗指標都在那份，這裡不重複）。
> 本文件回答：**選哪些題目、實驗怎麼設計、要寫哪些程式、照什麼順序做。**
>
> 狀態：**提案中，尚未動工。** 文中所有探測數字都在暫存區跑出，專案程式碼未改動。

**實驗題目（易／中／難）：** Best Time to Buy and Sell Stock（LC121）／Longest Substring Without Repeating Characters（LC3）／Longest Valid Parentheses（LC32）
**收斂條件：** TPR = 1.0、每個 S- 至少被抓一次、**TNR 達成率**（TNR ÷ 該題上限）≥ 0.85；每題上限 4 輪

---

## 一、選題

### 1.1 為什麼要換掉原本的第 2、3 題

原本的易／中／難是 Valid Parentheses（VP）／Longest Substring（LS）／Median of Two Sorted Arrays（MED）。對這個實驗架構有兩個問題：

| 問題 | 說明 | 後果 |
|---|---|---|
| **難度和輸出型態綁在一起** | 只有「易」那題（VP）是布林輸出（B 類），TNR 上限只有 0.667 | VP 若表現不同，分不清是「題目簡單」還是「輸出是布林」造成的 |
| **「難」題難在效率，不在邏輯** | MED 的 hard 來自 O(log(m+n)) 要求，但 TPR/TNR 只驗證答案對不對；`sorted(nums1+nums2)` 一樣全過 | 測資角度來看 MED 其實不難，「方法能用在難題上」的主張站不住 |

### 1.2 選題標準

1. 通過第四節的適用性判斷（Q1），且第四關判定適合當實驗題（Q2）
2. **難度要反映在「正確性」上**：難題要有比較多、比較隱蔽的錯誤寫法，而不是難在效率要求
3. **輸出型態一致**：三題都是整數輸出，讓難度成為主要變因
4. 能寫出 3 個寫法不同、且彼此答案一致的 S+
5. 能列出 6 種真實初學者會犯的 S- 錯誤

### 1.3 選定的題目（暫存區探測結果）

| 難度 | 題目 | 輸入 → 輸出 | S+ 一致性 | 第 0 輪：只用 LC 官方範例 | TNR 上限 | 第 0 輪達成率 |
|---|---|---|---|---|---|---|
| 易 | **LC121** Best Time to Buy and Sell Stock | list[int] → int | 2 萬組隨機輸入 0 次不一致 | TNR 0.500，抓到 5/6 種錯 | 0.833 | 0.60 |
| 中 | **LC3** Longest Substring（沿用） | str → int | 已驗證 | 原始 18 筆：TNR 0.491，6/6 | 1.000 | 0.49 |
| 難 | **LC32** Longest Valid Parentheses | str → int | 2 萬組隨機輸入 0 次不一致 | TNR 0.278，**只抓到 4/6 種錯** | 1.000 | **0.28** |

起點達成率依難度遞減（0.60 → 0.49 → 0.28），代表**題目越難，憑經驗設計的測資越抓不到錯**，正好是 AI 輔助最該發揮作用的地方。

**淘汰的候選：** LC42 Trapping Rain Water。三個 S+ 一致、上限 1.0，但只用官方範例 TNR 就有 0.833，幾乎沒有進步空間，不適合當實驗題。

### 1.4 草擬的 S+ / S- 池

**LC121 Best Time to Buy and Sell Stock**

| S+ | S- |
|---|---|
| 一次掃描，記錄目前最低價 | `max_minus_min`：直接 `max(p) - min(p)`，忽略「先買後賣」 |
| 雙層迴圈暴力解 | `no_clamp_zero`：利潤初值設成第一天差價，沒有獲利時回傳負數 |
| 對每日價差做 Kadane | `adjacent_only`：只看相鄰兩天的差價 |
| | `sum_positive_diffs`：把所有上漲加總（誤解成可以多次買賣） |
| | `skip_last_day`：迴圈少跑最後一天 |
| | `buy_first_day`：固定第一天買進 |

**LC32 Longest Valid Parentheses**

| S+ | S- |
|---|---|
| stack 存索引，底部放基準點 | `total_pairs`：算全部能配對的括號數，不管是否連續 |
| 左右各掃一次計數 | `left_scan_only`：只從左往右掃，漏掉 `(()` 這類情況 |
| 暴力檢查每個子字串 | `no_concat`：只算單一配對區段，沒把相鄰的 `()()` 接起來 |
| | `max_depth`：回傳最大巢狀深度 × 2 |
| | `reset_without_base`：遇到多的 `)` 重設起點，但沒處理剩下的 `(` |
| | `count_adjacent_pairs`：只認相鄰的 `()`，不認巢狀的 `(())` |

LC3 沿用現有的 `solutions_correct/`、`solutions_wrong/`。

### 1.5 原本的 VP、MED 怎麼處理

- **留在平台上**，學生照常可以練習，不影響線上服務。
- **不進主要實驗。** VP 的分析保留在第五節，當作「為什麼要改用達成率」的實證；MED 列為「只考效率」的不適用例子。
- 原本規劃的「VP 刪除空字串測資」不再需要做（VP 不再是實驗題）；這筆違反 constraints 的問題另列為平台小修正。

## 二、實驗設計

### 研究問題

> 「AI 提案 + 客觀評測 + 數字優先的人工審核」能否：
> 1. 在**同一題**上達到與純人工迭代相當的品質？（實驗一）
> 2. 推廣到**不同難度**的題目，且品質不打折、人工負擔低？（實驗二）

### 實驗一：同題對照（LC3）

| | 人工迭代（已完成） | AI 輔助（新） |
|---|---|---|
| 起點 | 原始 18 筆，TNR 0.491 | 同一份 18 筆 |
| S+／S- 池 | 3 + 6 | 同一組 |
| 流程 | 人分析回饋 → 改生成器 | AI 提案 → 評測 → 人審核 |
| 比較 | 4 輪、TNR 0.882、**驗收 TNR 0.471** | 輪數、最終 TNR、人工細看比例、**驗收 TNR** |

**這是最直接的對照：** 同一題、同一個起點、同一組錯誤解，只差在測資是誰想的。除了比訓練池 TNR，也比**驗收 TNR**：人工版只有 0.471，AI 輔助版是否泛化得更好，是這個實驗新的觀察重點。

> 限制：審核者已經知道 LC3 的最佳解法（combo_kill），審核判斷可能受影響。緩解方式：審核只看數字做決定，且 AI 的 prompt 不包含任何人工迭代的結果。論文列為研究限制。

### 實驗二：難度梯度（LC121、LC3、LC32）

- 新題目的**第 0 輪統一定義為「只用 LeetCode 官方範例」**，模擬出題者憑直覺給的最基本測資
- LC3 直接使用實驗一的 AI 輔助結果
- 比較三題的：收斂輪數、最終達成率、人工細看比例、`target_hit` 率、validator 擋掉率
- 觀察重點：難度越高，AI 輔助帶來的進步是否越大（起點越低，進步空間越大）

### 指標（沿用已定案決策）

| 指標 | 定義 |
|---|---|
| 收斂輪數 | 達到收斂條件花了幾輪 |
| 最終 TNR 達成率 | TNR ÷ 該題上限 |
| 人工細看比例（主要效率指標） | 模糊區候選數 ÷ 全部候選 |
| 分流省下的時間 | 「模糊區平均每筆秒數 × 全部候選數」−「實際審核秒數」 |
| `target_hit` 率 | AI 宣稱要抓的錯誤，實際有抓到的比例 |
| validator 擋掉率 | AI 提出的不合法輸入比例 |
| 看理由後改判次數 | 人先判斷、看了 AI 理由後改變決定的次數 |
| **驗收 TNR（泛化能力）** | 最終測資在「驗收用錯誤解」上的 TNR，與訓練池 TNR 的落差 |

### 穩定測資的定義（驗收標準）

本研究的產出是「可以直接給平台使用的穩定測資」。一份測資必須**同時符合以下 4 項**才算穩定：

| # | 面向 | 標準 | 檢查方式 |
|---|---|---|---|
| **S1** | 品質達標 | TPR = 1.0、訓練池每個 S- 至少被抓一次、TNR 達成率 ≥ 0.85 | `run_eval` |
| **S2** | **泛化** | **驗收池每個錯誤解至少被抓一次**；另外回報驗收 TNR | 最後一輪結束後跑一次 |
| **S3** | 可重現 | 每輪的候選、評測、審核紀錄都存檔；**不必再呼叫 AI**，只靠紀錄就能重建同一份測資 | `rounds/` 目錄 + 重建腳本 |
| **S4** | 不會退化 | pytest 品質守門員對該題檢查 S1、S2，之後任何人改測資都會被擋 | `test_problem_quality.py` |

#### 為什麼一定要有 S2：訓練池和驗收池要分開

測資是針對訓練池（6 個 S-）一輪一輪改出來的，再用同一個池子打分數，等於**用考古題出題、又用同一份考古題驗收**。測資可能只學會抓這 6 種錯，遇到沒見過的錯誤就失靈。

**這個問題已經實際發生在 LC3（暫存區實測）：**

| | 訓練池（6 個 S-） | 驗收池（3 個新錯誤解） |
|---|---|---|
| 現行上線的 v4 17 筆 TNR | **0.882** | **0.471** |

驗收池裡的 `no_max_left`（用 dict 記錄位置但更新 left 時忘了取 max）就是經典的 `"abba"` 錯誤（回傳 3，正解 2）。17 筆測資**只有 1 筆**抓到它，而且那一筆（`beebcedfeaeadcebbfde`）是隨機產生的字串，不是刻意設計的。只要換掉那一筆，這個常見錯誤就會完全漏網。

#### 驗收池（每題 3 個，暫存區已驗證：會答錯、且與訓練池行為不重複）

| 題目 | 驗收用錯誤解 | 目前測資抓到 |
|---|---|---|
| LC3 | `if_not_while`：遇到重複字元只移除一次（用 if 而不是 while） | 12/17 |
| | `no_max_left`：dict 版更新 left 時沒取 max（`"abba"` 錯誤） | **1/17** |
| | `update_only_on_dup`：只在遇到重複時更新答案，漏掉結尾的視窗 | 11/17 |
| LC121 | `global_min_then_max`：先找全域最低點，只看它之後的最高價 | **0/2**（官方範例） |
| | `init_min_zero`：最低價初值設成 0 而不是第一天價格 | 2/2 |
| | `first_valley_peak`：只算第一段「谷底到山頂」 | 1/2 |
| LC32 | `forget_new_base`：stack 清空後忘了放入新的基準點 | 1/3 |
| | `right_scan_only`：只從右往左掃 | 1/3 |
| | `dp_missing_concat`：DP 版漏掉「接上前面合法區段」那一項 | **0/3**（官方範例） |

#### 驗收池的使用規則

1. **迭代期間完全不碰。** AI 的 prompt 不包含驗收池；`score_candidates.py` 和 `review.py` 只顯示訓練池的結果，審核者也看不到驗收池的分數。
2. **只在最後一輪結束後跑一次。**
3. **沒通過 S2 就照實回報**，不能看了驗收結果再回頭改測資。否則驗收池就變成訓練池，失去意義。
4. 若為了上線需要補強，可以在實驗紀錄**凍結之後**另外做一輪，並在論文中標明這是實驗之外的修正。

> 限制：驗收池和訓練池由同一人設計，仍可能有共同盲點。論文列為研究限制；理想做法是由第二人獨立設計驗收池。

## 三、總體規劃

### 里程碑

| 里程碑 | 包含階段 | 估計工時 | 交付成果 | 完成後就能報告的內容 |
|---|---|---|---|---|
| **M1 基準建立** | Phase 0–1 | 2 週 | 多題目評測工具、LC121／LC32 題目上架、S+/S- 池、validator、上限估算 | 三題的第 0 輪達成率（難度梯度的起點） |
| **M2 工具完成** | Phase 2–4 | 1.5–2 週 | `propose.py`、`score_candidates.py`、`review.py` | 完整流程可以試跑一輪 |
| **M3 實驗一** | Phase 5（LC3） | 1 週 | LC3 AI 輔助迭代紀錄 | 人工 vs AI 的同題對照 |
| **M4 實驗二** | Phase 5（LC121、LC32） | 1.5 週 | 兩題迭代紀錄 | 難度梯度比較 |
| **M5 收尾** | Phase 6–7 | 1.5–2 週 | 新測資上線、論文章節、口頭報告投影片 | 完整結論 |
| | | **合計約 8–9 週** | | |

### 範圍控制（時間不夠時怎麼砍）

| 情況 | 做法 |
|---|---|
| 只剩約一半時間 | 只做實驗一（LC3 同題對照）＋ LC32；LC121 寫成未來工作 |
| 再更少 | 只做實驗一，難度推廣列為未來工作 |
| 審核介面來不及 | 維持 CLI；口頭報告用終端機截圖說明「數字先、理由後」 |
| 8B／70B 比較 | 屬選做，第一個砍 |

### 風險與備案

| 風險 | 可能結果 | 備案 |
|---|---|---|
| AI 提案品質差 | 收斂不了或輪數很多 | 本身就是可報告的結果（validator 擋掉率、`target_hit` 率）；同一套工具可改回人工提案 |
| S- 池由同一人設計 | TNR 被高估 | 每個 S- 檔頭寫明錯誤來源；論文列為研究限制 |
| 實驗一的審核者已知答案 | 對照偏向 AI | 審核只依數字；AI prompt 不含人工迭代結果；列為限制 |
| Groq 模型下架或限流 | 實驗中斷 | 提案程式可換模型；每輪候選都存檔，可以接續 |
| 只有三題、一位審核者 | 推廣性有限 | 定位為「可行性驗證」，不宣稱普遍有效 |

### 預期貢獻

1. 把 TPR/TNR 測資品質方法論從單一題目推廣到多題目的**工具鏈**
2. **TNR 達成率**：修正固定門檻在不同題目間不可比的問題（第五節）
3. 一套**有文獻依據的人機協作流程**：AI 不給答案、數字先於理由、回饋結構化
4. **同題對照 + 難度梯度**兩組可重現的實驗數據
5. **訓練池／驗收池分離**：指出並量化「測資對錯誤解池過度擬合」的問題（LC3：0.882 vs 0.471），並把泛化能力納入穩定測資的驗收標準

## 四、題目適用性判斷方法論

### 4.1 兩個問題要分開判斷

| 問題 | 回答什麼 | 適用對象 |
|---|---|---|
| **Q1 適用性** | 這套方法能不能用在這題？ | 任何想導入方法的題目 |
| **Q2 實驗價值** | 這題適不適合當本研究的實驗題？ | 只有挑實驗題時才需要 |

一題可以「適用但不適合當實驗題」（例如 LC42：方法完全可用，但起點已經太高，看不出改進）。

### 4.2 判斷流程：四關

```
第一關 靜態篩選（只讀題目，約 10 分鐘）
   │  違反平台限制 → 🔧 需擴充後適用（停）
   │  違反方法限制 → ❌ 不適用（停）
   ▼
第二關 建池驗證（寫 S+/S-/validator，約半天）
   │  S+ 不一致 → 回頭檢查「答案是否唯一」
   │  有效 S- 少於 4 個 → 補 S- 或判 ❌
   ▼
第三關 量化（估上限、算起點）
   │  → 判定 ✅ A 級（上限 = 1）或 ✅ B 級（上限 < 1，用達成率）
   ▼  ─────── 到這裡回答完 Q1 ───────
第四關 實驗價值（只有挑實驗題時才做）
      → 適合／不適合當實驗題
```

#### 第一關：靜態篩選

逐條檢查第 4 節末「附表一：必要條件」的 7 條，只需要讀題目敘述：

| 結果 | 判定 |
|---|---|
| 7 條全過 | 進第二關 |
| 違反第 1–3 條（平台限制） | 🔧 **需擴充後適用**：照「附表二」的擴充方式改平台後可以重新判斷 |
| 違反第 4 或 6 條（方法限制） | ❌ **不適用** |
| 全過，但題目的難度來自效率要求 | 繼續，但標註 ⚠️ **只驗證正確性** |

#### 第二關：建池驗證

| 檢查 | 做法 | 通過標準 | 不通過代表 |
|---|---|---|---|
| **2a S+ 一致性** | 寫 3 種演算法不同的正確解，在 2 萬組隨機合法輸入上比對答案 | 不一致 0 次 | 某個 S+ 寫錯，或答案其實不唯一（回到第 4 條） |
| **2b S- 非等價** | 每個 S- 至少在一組輸入上答錯 | 全部 S- 都被抓過 | 這個「錯誤解」其實是正確的，要刪掉 |
| **2c S- 不重複** | 比較每兩個 S- 被抓到的輸入集合 | 沒有兩個完全相同 | 兩個 S- 其實是同一種錯，只能算一個 |
| **2d 有效 S- 數** | 扣掉等價與重複後的 S- 數 | ≥ 4 | S- 池鑑別力不足（第 7 條） |
| **2e validator** | 官方範例都要通過 validator；S+ 在 validator 通過的輸入上不能當掉 | 全部通過 | validator 太嚴或太鬆 |

另外記錄 S- 之間的**包含關係**（抓到 a 的輸入一定也抓到 b）。這不算失敗，但包含關係越多，代表錯誤越容易被一起抓到，第 0 輪 TNR 會偏高。

#### 第三關：量化

| 檢查 | 做法 | 用途 |
|---|---|---|
| **3a TNR 上限** | 小輸入窮舉 + 隨機搜尋，找出「單筆最多抓到幾個 S-」÷ S- 總數 | 決定分級；作為達成率的分母 |
| **3b 第 0 輪起點** | 只用 LeetCode 官方範例跑 TPR/TNR | 起點達成率 = 第 0 輪 TNR ÷ 上限 |

## 五、為什麼固定門檻「TNR ≥ 0.85」會失效

### 探測結果

| 題目 | 輸出 | 測資來源 | TNR | 單筆最多抓到 | **TNR 上限** |
|---|---|---|---|---|---|
| LC3 Longest Substring | 整數 | 原始 18 筆 → v4 | 0.491 → 0.882 | 6/6 | 1.000 |
| LC32 Longest Valid Parentheses | 整數 | LC 官方範例 | 0.278 | 6/6 | 1.000 |
| LC121 Best Time to Buy and Sell Stock | 整數 | LC 官方範例 | 0.500 | **5/6** | **0.833** |
| Valid Parentheses | 布林 | 平台現有 11 筆 | 0.212 | **4/6** | **0.667** |
| Median | 浮點數 | 平台現有 11 筆 | 0.470 | 6/6 | 1.000 |

Valid Parentheses 窮舉了長度 1–8 的全部 201 萬個輸入；LC121 窮舉了長度 1–6、數值 0–4 的全部輸入；其他題目都已找到抓到 6/6 的例子，上限確定是 1.0。

### 第一步：TNR 其實是在算「每筆測資平均抓到幾種錯」

現行 TNR = 每個錯誤解「被擋下的測資比例」取平均。換個角度數同一張表：

```
TNR = （每筆測資各自抓到幾個錯誤解，加總）÷（測資數 × 錯誤解數）
    = 每筆測資平均抓到的錯誤解數 ÷ 錯誤解總數
```

所以如果整份測資裡**最強的那一筆**也只能同時抓到 4 種錯，平均就不可能超過 4，TNR 上限就是 4 ÷ 6 = 0.667。測資再多、再換組合都一樣，因為平均值不可能高過最大值。

### 第二步：為什麼有些題目沒有一筆能抓到全部的錯

**Valid Parentheses** 的代表性輸入（實測）：

| 輸入 | 正確答案 | 抓到的錯誤解 | 抓到數 |
|---|---|---|---|
| `([)]` | False | count_only、stack_not_checked、no_type_check、running_balance | **4** |
| `}{` | False | count_only、stack_not_checked、empty_pop_crash | 3 |
| `]` | False | stack_not_checked、empty_pop_crash | 2 |
| `(` | False | stack_not_checked | 1 |
| `(())` | True | single_pass_replace | 1 |

兩個結構性原因：

1. **錯誤只在特定答案時才會露出來。**
   - 「太寬鬆」的錯誤（count_only、stack_not_checked、no_type_check、running_balance）把不合法的字串誤判成 True，**只有答案是 False 的測資抓得到**。
   - 「太嚴格」的錯誤（single_pass_replace）把合法的巢狀字串誤判成 False，**只有答案是 True 的測資抓得到**。
   - 一筆測資只有一個答案，兩邊的錯誤不可能在同一筆一起被抓到。
2. **有些錯誤的觸發條件互相矛盾。**
   - empty_pop_crash 要出錯，字串中必須有「右括號前面沒有可配對的左括號」（例如開頭就是 `]`）。
   - 一旦出現這種情況，no_type_check 和 running_balance 都會正確回答 False，反而抓不到。

**LC121 也有同樣的現象，雖然它輸出的是整數：**
- `no_clamp_zero` 只有在「完全沒辦法獲利、正確答案是 0」時才會出錯（它會回傳負數）。
- 但答案是 0 的輸入（股價一路往下跌）幾乎抓不到其他錯誤：`adjacent_only`、`sum_positive_diffs`、`skip_last_day`、`buy_first_day` 在這種輸入下也都剛好回答 0。
- 窮舉結果：能抓到 5 種錯的輸入（如 `[2,3,0,1,2]`）一定漏掉 `no_clamp_zero`，所以上限是 5/6。

### 第三步：一般化

真正的原因不是「輸出是布林」，而是 **某些錯誤只在特定的答案值才會露出來**（答案是 False、答案是 0……）。

- 輸出越少種可能值（布林、少數選項），這種狀況越常發生，上限越低。
- 但整數輸出的題目，只要有錯誤專門在邊界答案（例如 0）出錯，也一樣會碰到。

上限是**題目和錯誤池本身的性質**，跟 AI 或測資設計者的能力無關。所以門檻應該跟各題自己的上限比，而不是全部套用同一個數字。

### 修正後的收斂條件

- **主要條件：** TPR = 1.0，且**每個 S- 至少被抓一次**（軟體測試的 mutation score = 100%）
- **品質指標：** **TNR 達成率 = TNR ÷ 該題 TNR 上限 ≥ 0.85**
- 上限用窮舉（輸入空間小時）或隨機搜尋估計，併入 Phase 1
- LC3 的上限是 1.0，所以達成率 = 0.882，原本的數字和結論不受影響

### Phase 3：評測 + 分流 `testgen/score_candidates.py`

對每一筆候選**單獨**跑 S+/S-：

| 欄位 | 意義 |
|---|---|
| `s_plus_ok` | 3 個 S+ 是否全過（應恆真，否則代表某個 S+ 有問題） |
| `kills` | 打掉哪些 S- |
| `new_kills` | 打掉了**目前正式測資集還抓不太到**的 S- 有幾個 |
| `delta_tnr` | 併入正式集之後 TNR 的變化 |
| `target_hit` | AI 說的 `target_bug` 是否真的在 `kills` 裡 |

分流：
- **快速通過：** `delta_tnr` 明顯為正 → 預設採用，只需人按確認
- **快速淘汰：** `s_plus_ok=False` 或 `kills` 為空 → 預設丟棄，只需人按確認
- **模糊區：** 其他 → 人工細看

### Phase 4：人工審核介面 `testgen/review.py`（CLI）

逐筆顯示，順序固定：

1. 候選輸入 + expected + `kills` + `delta_tnr` + 分流標籤
2. **人先輸入裁決**（留下／丟棄／修改後留下）
3. 裁決送出後才能按 `r` 查看 AI 理由；看完可以改判，但**改判會另外記錄**

每筆記錄裁決、是否看過理由、是否改判、從顯示到裁決的秒數 → `rounds/r{N}_review.json`。
通過的候選併入 `rounds/r{N}_tests.py`，重跑 `run_eval` 得到這輪正式 TPR/TNR。

## 八、全自動流程（2026-10-13 起）

### 研究問題（修訂）

> 「AI 提案 + 客觀評測 + 依數字自動審核」的全自動流程，能不能在不同難度的題目上從頭跑到尾，並讓測資品質（訓練池 TNR、驗收池 TNR）比起點進步？

### 流程

一個指令：`python -m testgen.pipeline --problem <id>`（先用 `--plan` 看狀態，不呼叫 API、不寫檔）

每輪：`propose.py` 提案 → `auto_review.py` 自動審核。停止條件依序：收斂（TPR = 1、訓練池無漏網、達成率 ≥ 0.85）→ 停滯（上一輪沒保留新測資）→ 達到輪數上限（4）。結束後驗收池只跑一次，存成 `rounds/heldout_final.json`；每輪數據彙整成 `rounds/pipeline_summary.json`。

**自動審核規則：** 只看評測數字，不看 AI 理由；上一輪正式測資全保留；候選以貪婪法加入，每次挑「加入後 TNR 最高」的一筆，TNR 不再提高就停。`auto_review.py` 對 LC121 r1–r3、LC32 r1–r5 重算，評測與保留數**全部和原本紀錄一致**。

**流程預設參數：** `openai/gpt-oss-120b`、temperature 0.7、每輪 12 筆、prompt v2、`--reasoning-effort low`、回覆上限 4000 tokens。Groq 免費方案每分鐘上限 8000 tokens（prompt + 回覆上限一起算），不壓低就會在 prompt 變長的後幾輪被拒（LC3 第 4 輪實際發生）。

### 結果

| 題目 | 起點 TNR | 最終 TNR | 達成率 | 輪數 | 停止原因 | 最終測資數 | 驗收池 TNR | 驗收池漏網 |
|---|---|---|---|---|---|---|---|---|
| LC121（易） | 0.500 | 0.583 | 0.70 | 3 | 停滯 | 4 | 0.417 | `global_min_then_max` |
| LC32（難） | 0.278 | 0.676 | 0.68 | 5 | 輪數上限 | 54 | 0.537 | 無 |

- **流程能運行：** LC121、LC32 都從頭跑到結束，沒有人工介入；LC32 驗收池沒有漏網。
- **三題都沒有收斂**（達成率都低於 0.85）。LC121 停滯的原因是貪婪規則：只收「提高平均」的候選，只抓到少數錯誤的測資即使能補漏洞也會被拒，所以只剩 4 道（K15），驗收池也因此漏掉 `global_min_then_max`（K13）。
- **LC3：** 2026-10-13 曾用 pipeline 跑過全自動 4 輪以驗證流程，但與 K12「不補輪次」的決定不一致，**負責人決定刪除該紀錄（K16）**，論文不引用。LC3 維持人工迭代的結果（訓練池 0.889、驗收池 0.47）。
