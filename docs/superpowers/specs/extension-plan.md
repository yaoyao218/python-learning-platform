# 延伸思考六項：問題、解法、論文佐證（提案版）

**定位**：這次專題停在「提案＋環境測試」，**不做準度與效度的驗證**。重點是把問題講清楚、提出解法，並指出有哪些論文的方法可以借來支撐。
所以這份文件不寫成功門檻、不寫統計驗證；每一項只回答三件事：
1. 現在的問題是什麼
2. 打算怎麼解
3. 哪篇論文用過類似的方法、可以拿來佐證

「環境測試」只確認一件事：做出來的東西**跑得動、不會壞**，不代表有效。
簡報不放這些，報告後口頭簡述。

## 1. 分階段提示（提示無效時一階一階升級）

**問題**：現在只有一種提示。學生看了還是卡住時沒有下一步；直接給完整程式碼又沒學到東西，還和「AI 看不到學生程式」衝突。

> 與測試用虛擬碼的關係（見 `2026-10-10-ai-pool-bootstrapping-design.md` 第十五節）：測試用虛擬碼是事前給的、已驗證正確的任務規格；第 4 階偽代碼是卡關後的介入提示，角色不同。若使用者一開始就有虛擬碼，第 4 階就變得多餘，升階設計需改成針對偏差步驟的回饋。

**解法**
- 第 1–3 階（維持看不到學生程式碼）：方向 → 細節 → 針對哪道測資錯了的分析。
- 第 4 階：偽代碼或步驟骨架，不給能直接貼上的程式碼。
- 升階規則：同一階提示後連續失敗 3 次就升一階，通過就回到最前面。

**論文佐證**
- P1 就是分四層的提示設計，且發現只給高層的文字提示，新手常常「沒幫助甚至被誤導」，補上較具體的例子才有用——正好支持「卡住就要往下一階升」。
- P2 說明「給偽代碼、不給程式碼」是已有人實作過的折衷。
- P3 說明「在提示輸出端加護欄」的做法，和我們已有的檢查關是同一類。
- 我們和 P1 的差別：他們最底層是給程式碼，我們不給。

**環境測試**：連續失敗 3 次確實升階、通過後回到第 1 階、檢查關會擋下第 4 階輸出中的程式碼。⚠️ 需先確認後端有沒有記錄每位學生的提交次數。

## 2. 遮照填空（最後一階）

**問題**：第 4 階後學生還是卡住，又不能直接給答案。

**解法**：挖洞的對象是**標準答案**，不是學生程式。把關鍵語法（條件、迴圈範圍、關鍵變數更新）挖掉做成填空題；「挖多少洞」作為可調參數。

**論文佐證**
- P4：Faded Parsons 就是「把程式拆開加挖空，讓學生補」，報告在教授程式模式上優於單純寫程式和讀程式。
- P5：把填空（偏語法）和偽代碼重組（偏概念）做成學生可選的鷹架，並指出學生會依需要選擇——可借來說明為什麼最後一階要提供填空而非只是更多文字。
- 我們和他們的差別：他們的填空從固定練習題來，我們是在學生卡關時才出現，並由標準答案產生。

**環境測試**：能從標準答案自動產生填空版本，填回原內容後測資全過；挖洞後版本不會直接通過測資。

**實作狀態（2026-10-14）**：已上線。`backend/cloze.py` 用 AST 從 testgen registry 的標準答案挑關鍵部分挖洞（條件 → 迴圈內更新 → 迴圈範圍 → return 值 → 初始值 → 迴圈內呼叫的參數，最多 5 個，空容器與單一變數不挖），`GET /problems/{id}/cloze` 只送挖洞後的程式碼；前端 `ClozePanel.vue` 在同一題連續 3 次沒通過後顯示，通過就收起，次數存在瀏覽器。上面的環境測試在 `backend/tests/test_cloze.py`，五題都通過。第 1–4 階的升階提示尚未實作（目前是固定一種 AI 提示，加上題目頁一直可看的虛擬碼）。

## 3. 學習成效量化

**問題**：現在只量「測資好不好」，沒量「學生有沒有學到」。

**解法（提案）**：把實驗設計寫成可以直接用的說明——分組（無提示／只有提示／完整升階）、記錄項目（嘗試次數、完成時間、後測）、同意書與學校規定確認。

**論文佐證**
- P6 是現成的設計範本：新手分兩組（有無 AI 輔助），比完成率，再用「手動修改」任務檢查有沒有依賴 AI。
- P2 提供另一條路：大規模課堂部署，用使用紀錄加問卷加訪談，不做對照組。
- P1、P5 提供小規模路線：10 人上下的出聲思考研究，先找出問題而不是證明效果。

**本專題做到哪**：只寫到「實驗說明書」這層，不執行，也不宣稱效果。

## 4. 自動標籤系統

**問題**：每個錯誤程式屬於哪種錯，現在靠人工標，很花時間。

**解法**：讓 AI 讀（去掉標記的）程式判斷屬於哪一類，人再覆核。

**論文佐證**
- P7：用 ChatGPT 辨識新手錯誤是有人做過的，且是為了讓老師看到整體概況，而不是取代人。
- P8：提供現成的錯誤分類法（十類），可借來當我們標籤的分類架構，避免自己亂訂。

**環境測試**：把現有的小檢查（9 份樣本、各問 3 次）整合成可重跑的腳本。不報準確率結論。

## 5. 題庫擴充與跨題目驗證

**問題**：只有 3 題做過測資實驗、只有 1 題做了多輪，不知道方法能不能用在別題。

**解法**：把同一套流程複製到另外 2 題，每題先過現有的品質檢查（正解一致、錯解有效、留出池有效）。

**論文佐證**
- P9：用 500 題、10 萬份解答評測測資，且分成「覆蓋面」和「抓出指定錯誤」兩種衡量；說明跨大量題目評測是這個領域的常見做法，也點出我們的規模（3 題）只是起步。

**環境測試**：新題目放進去後，現有的檢查流程跑得起來。

## 6. 加強安全執行

**問題**：現在只擋不小心的誤用；`open`、`eval` 沒擋，也沒有記憶體或時間上限。

**解法**：擋危險內建函式、加時間與記憶體上限；進一步用獨立程序或容器隔離。

**論文佐證**
- P10：edX CodeJail（AppArmor）與 Epicbox（Docker）是線上教學平台實際在用的做法，可限制 CPU、記憶體、時間、網路。

**環境測試**：準備一組「會越權的程式」（讀檔、無窮迴圈、吃記憶體），確認被擋或在限制內結束，且現有測試全過。
